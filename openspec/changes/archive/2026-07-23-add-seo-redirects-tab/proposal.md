# Proposal: Add SEO / Redirects Tab

## Problem Statement

The Monitor tab tracks uptime/status for user-added URLs, but gives no visibility into common on-page SEO hygiene signals: whether a URL's canonical form is consistent (www vs non-www, HTTP vs HTTPS, trailing slash vs none) and whether `robots.txt` / sitemap files are reachable. Users currently have no way to see or periodically re-verify these signals from within webmonitor, and would need external tools to catch canonicalization drift or a missing sitemap/robots file.

## Intent

Add a second "SEO / Redirects" tab, next to the existing "Monitor" tab, that surfaces five per-URL SEO checks (www redirect, HTTPS redirect, trailing-slash redirect, robots.txt reachability, sitemap reachability) for the **same shared list of URLs** already tracked by Monitor. Checks run periodically (like Monitor, but on their own, longer cadence) and are manually re-runnable per entry with immediate feedback. Results and a last-checked timestamp are persisted, with a lightweight history log mirroring the existing Monitor/MonitorLog pattern. The feature must not alter existing Monitor behavior and must minimize outbound HTTP requests per check cycle.

## Key Design Decisions (locked via clarifying-question round)

1. **Shared URL source of truth.** `monitors` remains the single table holding `name`/`url`/ownership for every tracked URL. There is no independent `seo_checks.url` field. `seo_checks` is a one-to-one child of `monitors` (`seo_checks.monitor_id` FK, unique). Adding a URL from *either* tab results in exactly one `monitors` row and exactly one linked `seo_checks` row, so both tabs always list the identical set of URLs. This is implemented via a `Monitor::created` event/observer that auto-creates the paired `seo_checks` row with default values, so the invariant "every monitor has exactly one seo_checks row" holds regardless of which tab the URL was added from.
2. **Two-table history split**, mirroring Monitor/MonitorLog: `seo_checks` holds the *current* state per URL (`monitor_id`, five check result columns, `interval`, `last_checked_at`, timestamps); `seo_check_logs` holds append-only history rows (`seo_check_id`, the five result values at that point, `checked_at`, timestamps), deduplicated on write the same way `MonitoringService::recordLog()` avoids inserting unchanged consecutive rows.
3. **Independent scheduling cadence.** `seo_checks.interval` (minutes) is separate from `monitors.interval` and defaults to a much longer period (e.g. 1440 = daily) since SEO signals change far less often than uptime. The periodic scheduler adds its own `Schedule::call(...)->everyMinute()` block in `routes/console.php` that iterates `SeoCheck::cursor()` and dispatches `CheckSeoJob` when `last_checked_at` is null or `interval` has elapsed — structurally identical to the existing Monitor loop, but fully decoupled so SEO checks never run on Monitor's frequent uptime cadence.
4. **Synchronous manual re-check.** `POST /seo/{seoCheck}/recheck` calls `CheckSeoJob::dispatchSync($seoCheck)` inline in the request (not queued), guaranteeing the redirect back to `seo.index` shows freshly computed results regardless of `QUEUE_CONNECTION`. The periodic scheduler still uses normal `dispatch()` (queued), consistent with `CheckMonitorJob`.
5. **Request-minimizing check design (hard constraint).** Rather than firing one outbound request per check (which would need up to 3 separate requests just for www/https/trailing-slash variants, plus 1 for robots.txt, plus up to 2 for sitemap — 5-7 requests per cycle), the new `SeoCheckService` uses a single **redirect probe** request per cycle to resolve all three canonicalization checks at once:
   - Issue one `GET` to the monitor's stored URL with `allow_redirects => false`.
   - If the response is a 3xx with a `Location` header, parse both the original URL and the `Location` target (scheme, host, path) and diff them: a host difference of exactly the `www.` prefix yields the www result (`www→no-www` / `no-www→www`); a scheme difference yields the HTTPS result (`http→https` / `https→http`); a path difference of exactly a trailing `/` yields the trailing-slash result (`with /` / `without /`). Any dimension that doesn't differ is `none`.
   - If the response is not a redirect (e.g. 200, or a redirect whose target changes none of these three dimensions), all three checks are recorded as `none` from that same single request — no extra probing requests are issued for www/https/trailing-slash.
   - `robots.txt` is 1 additional `GET {origin}/robots.txt` checked for a 200 status.
   - `sitemap` first tries `GET {origin}/sitemap.xml`; only if that does not return 200 does it fall back to a second `GET {origin}/sitemap_index.xml`. This keeps the worst case at 2 requests and the common case (a site with `sitemap.xml`) at 1.
   - **Total per cycle: 3 requests in the common case (redirect probe + robots + sitemap.xml hit), 4 in the worst case (sitemap fallback needed).** This is a deliberate tradeoff documented here: it trades a small amount of check granularity (e.g. if the URL happens not to redirect at all, we cannot separately probe "would www.example.com redirect somewhere different" — we only observe the actual redirect behavior of the stored URL, which is the behavior an end user/search engine would actually encounter) for a 2-3x reduction in outbound requests per entry per cycle, which matters at scale given this runs on a schedule across all shared URLs.
6. All five checks use the Guzzle client with `allow_redirects => false` explicitly and `http_errors => false`, isolated in the new `SeoCheckService` — the existing `MonitoringService`'s implicit redirect-following default for the uptime check is untouched.
7. **Form/UI reuse**: since URL creation is shared, the SEO tab gets its own minimal `seo/create.blade.php` (name + url fields only, reusing the same Tailwind input styling and `NoPrivateUrl` validation rule as Monitor's form) rather than refactoring Monitor's existing `create.blade.php` into a shared component. Submitting either form ends up creating the same underlying `Monitor` row (with SEO-tab submissions using sensible interval/timeout/expected_status_code defaults for the Monitor side, since those fields aren't exposed on the SEO form) plus its auto-created `seo_checks` row.
8. **UI language**: new SEO tab view labels follow the existing Spanish convention used in `monitors/*.blade.php` (e.g. "Añadir URL", "Nunca" for never-checked) for consistency with the rest of the authenticated UI; internal service/log messages may use English for clarity in new code, isolated from the pre-existing Catalan messages in `MonitoringService` (which are left untouched).
9. No per-entry SEO "show"/detail page and no SEO edit form are in scope — only list + add + manual re-check, per the task's explicit description of "a table."

## Scope

### In scope
- Migrations: `create_seo_checks_table` (one-to-one with `monitors` via `monitor_id` FK, cascade delete), `create_seo_check_logs_table` (FK to `seo_checks`, cascade delete), plus an index migration on `seo_checks.last_checked_at` mirroring the existing `monitors.last_checked_at` index, following the project's additive/one-migration-per-change convention.
- `Monitor` model: add `seoCheck(): HasOne` relation; add a `Monitor::created` listener (observer or `booted()` hook) that creates the paired `SeoCheck` row with default interval/state.
- New models: `SeoCheck` (fillable: `monitor_id, www_redirect, https_redirect, trailing_slash_redirect, robots_ok, sitemap_ok, interval, last_checked_at`; casts for booleans/enums and `last_checked_at => datetime`) and `SeoCheckLog` (fillable: `seo_check_id, www_redirect, https_redirect, trailing_slash_redirect, robots_ok, sitemap_ok, checked_at`).
- New `SeoCheckService` implementing the request-minimizing probe logic described above, injected with the same `GuzzleHttp\Client` DI pattern as `MonitoringService`.
- New `CheckSeoJob` (`ShouldQueue`, mirrors `CheckMonitorJob`'s `tries`/`backoff`), constructor takes `public SeoCheck $seoCheck`.
- New `SeoCheckController` with `index`, `create`, `store` (creates `Monitor` + relies on auto-created `SeoCheck`), and a `recheck` action (`POST /seo/{seoCheck}/recheck` → `CheckSeoJob::dispatchSync()` → redirect with flash message).
- New `StoreSeoCheckRequest` (name + url validation, reusing `NoPrivateUrl`).
- New `SeoCheckPolicy` scoped via the monitor's `user_id` (ownership check identical in spirit to `MonitorPolicy`), auto-discovered by Laravel naming convention.
- New Blade views: `resources/views/seo/index.blade.php` (table: name, url, one column per check with green/red/gray pill badges, "checked X ago" via `diffForHumans()`, per-row re-check button as a small POST form mirroring the existing delete-button pattern) and `resources/views/seo/create.blade.php` (name + url form).
- `routes/web.php`: add `Route::resource('seo', SeoCheckController::class)->only(['index','create','store'])` plus an explicit `Route::post('seo/{seoCheck}/recheck', ...)` inside the existing `auth` middleware group.
- `routes/console.php`: add a new, independent `Schedule::call(...)->everyMinute()` block iterating `SeoCheck::cursor()` and dispatching `CheckSeoJob::dispatch()` when due, decoupled from the existing Monitor scheduling block.
- `resources/views/layouts/navigation.blade.php`: add a second `<x-nav-link>` / `<x-responsive-nav-link>` pair for the new "SEO / Redirects" tab pointing at `route('seo.index')`, using `request()->routeIs('seo.*')` for active state — mirrors the existing Monitor nav-link lines exactly.
- Factory: `SeoCheckFactory` following the existing chainable-named-state pattern (e.g. `withWwwRedirect()`, `robotsMissing()`, `sitemapMissing()`).
- Tests: `tests/Feature/SeoCheckServiceTest.php` (Guzzle `MockHandler` + `Middleware::history`, asserting `allow_redirects=false` was set and asserting the reduced request count per scenario), `tests/Feature/SeoCheckControllerTest.php` (guest redirect, ownership isolation via the shared monitor's `user_id`, validation errors, cross-user `assertForbidden`, recheck flow asserting synchronous dispatch and updated `last_checked_at`), and a migration/model test confirming a `Monitor::create()` always yields exactly one paired `SeoCheck` row.

### Out of scope
- Any refactor of the existing `monitors/create.blade.php` into a shared Blade component — left untouched to avoid risk to existing functionality.
- Any change to `MonitoringService`'s existing (implicit) redirect-following behavior for uptime checks.
- A per-entry SEO "show"/detail page or history-browsing UI (the `seo_check_logs` table exists for future use but is not surfaced in any view in this change).
- Editing an existing SEO/Monitor entry's name or URL from the SEO tab (edit stays exclusively on the Monitor tab, since the URL record is shared and already editable there).
- A public/unauthenticated SEO status page (`public_token` pattern exists on Monitor but is not extended here).
- Role-based restrictions on the new routes (ownership-only, identical to Monitor's current model).
- Any new package/dependency — all checks use the already-available Guzzle client.

## Risks

- **Coupling risk via the `Monitor::created` hook**: introducing an observer/event on `Monitor` creation is a change to existing, working model behavior. Mitigation: keep the hook minimal (single insert of a `SeoCheck` row with defaults, wrapped so any failure there does not roll back or break Monitor creation — log and continue rather than throwing) and cover it with a dedicated test asserting Monitor creation still succeeds even in edge cases.
- **Request-count vs. granularity tradeoff**: the single-redirect-probe design (documented above) means a URL that does not itself redirect will report `none` for www/https/trailing-slash even if some *other* variant of that URL would redirect. This is an intentional, documented tradeoff to satisfy the "minimize HTTP requests" constraint; if finer-grained detection is later required, additional probe requests could be added as an opt-in, higher-cost mode.
- **Longer per-cycle latency for the SEO scheduler** compared to Monitor's single-request check (3-4 sequential requests vs. 1) — mitigated by the independent, longer default interval (daily-ish) so this does not compete with Monitor's frequent uptime cadence, and by keeping requests sequential (no new async/Pool complexity) for a first iteration, revisiting parallelization only if the daily cadence proves insufficient.
- **Synchronous dispatch on manual re-check** ties request duration to 3-4 outbound HTTP calls' worst-case latency (subject to Guzzle timeout); mitigated by applying a bounded per-request timeout (mirroring `MonitoringService`'s `timeout` option) so a single slow/unreachable URL cannot hang the controller indefinitely.
- **Schema coupling**: making `seo_checks.monitor_id` a required one-to-one FK means any future change to how Monitor entries are created/deleted must remain aware of the paired SeoCheck row (cascade delete handles removal; creation is handled by the new observer). This is a deliberate, documented dependency rather than an accidental one.
- **Language consistency**: new SEO Blade labels follow the existing Spanish UI convention while any new internal log/service messages may be English — documented explicitly here to avoid silently compounding the pre-existing Catalan/Spanish inconsistency without a stated rationale.

## Rollback

- All schema changes are additive, new tables (`seo_checks`, `seo_check_logs`) with `down()` methods that drop them — rolling back the migrations fully removes the feature's data with zero impact on `monitors`/`monitor_logs`.
- The only modification to an existing table's *behavior* is the new `Monitor::created` observer; removing the observer class/registration (and the two new migrations) fully reverts `Monitor` to its current behavior with no data loss to existing Monitor records.
- New routes, controller, views, job, service, and policy are additive files; removing them (and the nav-link edit in `navigation.blade.php`, and the new `routes/console.php` scheduling block) fully reverts the UI/route surface with no impact on Monitor routes/views.
- No existing migration, model, controller, or view for Monitor is modified in a way that changes its stored data or validation rules — a revert of this change's commit(s) is expected to be a clean, low-risk operation.

## Success Criteria

- A new "SEO / Redirects" nav tab appears next to "Monitor" in both desktop and mobile navigation, active-state highlighted via `request()->routeIs('seo.*')`, without altering the existing "Monitor" tab's markup or behavior.
- Adding a URL from either the Monitor tab or the SEO tab results in that URL appearing in both tabs' list views, backed by a single shared `monitors` row and exactly one linked `seo_checks` row.
- The SEO index table shows, per URL: www check, HTTPS check, trailing-slash check, robots.txt check, sitemap check (each as a colored pill: green for OK/normalized, red for a detected mismatch/failure, gray for "none"/not-applicable), plus a "checked X ago" relative-time column matching the existing Monitor tab's `diffForHumans()` pattern.
- Each row has a working manual re-check control that, when submitted, synchronously updates that entry's check results and `last_checked_at`, then redirects back to the SEO index showing the fresh values immediately (no dependency on a background queue worker running).
- The periodic scheduler dispatches SEO checks on their own per-entry interval, independent of and without altering Monitor's existing per-minute uptime scheduling loop.
- `SeoCheckService`'s outbound request count per check cycle is verified by test to be at most 4 (redirect probe + robots + up to 2 for sitemap), never one request per individual check dimension.
- All new and existing tests pass (`ddev exec vendor/bin/phpunit tests/`), including new `SeoCheckServiceTest` and `SeoCheckControllerTest` suites, with zero regressions in existing `MonitoringServiceTest`/`MonitorControllerTest` suites.
- `ddev phpcs` reports no new violations against `phpcs.xml`'s Drupal/DrupalPractice-derived rules as applied to this Laravel codebase's existing conventions (or, if not applicable to this Laravel project's actual lint config, the project's actual configured PHP linter/static analysis passes clean).
